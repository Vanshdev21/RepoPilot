RepoPilot connects to a public GitHub repository, understands a reported software problem,
uses Gemma 4 to investigate relevant code, prepares a possible fix, tests it in an isolated

1. Executive Summary
1.1 Product Overview
RepoPilot is an AI-powered open-source engineering agent that helps developers understand GitHub
repositories, investigate software issues, generate code patches, validate proposed fixes and prepare pull
requests.
Unlike a conventional AI chatbot, RepoPilot is organized around an end-to-end engineering workflow:
GitHub Issue → Repository Investigation → Root-Cause Analysis → Code Patch → Automated
Testing → Human Approval → Pull Request
1.2 Vision and Mission
Vision: Make meaningful open-source contributions accessible to every developer, regardless of experience with
unfamiliar codebases.
Mission: Reduce the time and technical complexity involved in understanding, investigating, fixing and
contributing to open-source software.
1.3 Product Promise
RepoPilot helps developers move from identifying a software problem to preparing a tested, reviewable
contribution. It does not autonomously merge code or guarantee that generated fixes are correct. Human
approval remains mandatory before publishing changes.
2. Problem Statement
Open-source development relies on contributors and maintainers who spend significant time investigating and
resolving software issues.
 • Understanding unfamiliar repositories and project conventions.
 • Identifying relevant files, functions and dependencies.
 • Investigating incomplete or complicated bug reports.
 • Reproducing software problems and identifying root causes.
 • Generating focused code fixes and appropriate tests.
 • Preparing clear pull requests and reviewing contributions.
 • Helping beginners make their first meaningful contribution.
 
2.1 Target Problem
A developer discovers a GitHub issue but does not know which files are responsible, what caused the problem,
how to reproduce it, how to implement a fix, whether the fix works or how to submit a contribution. RepoPilot
assists with these steps in one controlled workflow.

4.1 Primary Goals
 • Connect public GitHub repositories and retrieve their metadata and issues.
 • Understand enough repository context to investigate a selected issue.
 • Analyze and classify issues using Gemma 4.

 • Generate proposed code patches and validate them.
 • Execute tests in isolated Docker containers.

6. Functional Requirements
FR-01 — Authentication
Users authenticate through GitHub OAuth. Requirements: secure server-side token handling, session
management, logout, user profile retrieval and minimum required permissions. Acceptance: user can
authenticate; account identity is known; credentials are never exposed to the browser or AI model.
FR-02 — Repository Connection
Users submit a public GitHub repository URL. Validate it and retrieve owner, name, default branch, primary
language, description, README and repository tree. Acceptance: valid public repositories connect; invalid or
inaccessible repositories produce clear errors.
FR-03 — Issue Discovery
Retrieve and display actual open GitHub issues with title, description, number, labels and creation date. Support
pagination and exclude pull requests from the issue list. Acceptance: selecting an issue opens its details; API
failures are visible.
FR-04 — AI Issue Classification
Gemma 4 classifies issues as bug, feature request, documentation, enhancement, question or other. Return
summary, expected and actual behaviour, missing information, severity estimate and complexity estimate.
Acceptance: structured output is validated; estimates are labelled as estimates.
FR-05 — Duplicate Issue Detection
Compare issue titles and descriptions; use semantic similarity where available; display related candidates and
explain why they may be related. Acceptance: candidates are presented as suggestions; issues are never
automatically closed.
FR-06 — Repository Intelligence
Read README, retrieve file tree, identify languages and package manifests, inspect dependencies, search
filenames and symbols, and retrieve selected source files. Use GitHub API, bounded keyword/symbol search and
Tree-sitter where practical. Acceptance: inspected files are shown and retrieval respects size/context limits.
FR-07 — Root-Cause Investigation
Provide the issue and relevant source context to Gemma 4. Return possible causes, supporting evidence, files
that may need changes, uncertainty and missing information. Acceptance: structured findings reference
available source context and do not claim certainty without evidence.
FR-08 — Code Patch Generation
Generate unified diffs or structured file changes. Validate format and paths, reject path traversal, prevent writes
outside the workspace and show modifications for review. Acceptance: valid patches apply to the temporary
copy; invalid patches are rejected.

FR-09 — Docker Sandbox Execution
Test proposed changes in an isolated environment. Initially support Node.js projects. Create a temporary
workspace, apply the patch, use predefined runner images, execute approved commands, capture stdout/stderr,
exit code and duration, enforce resource limits and clean up. Acceptance: actual commands run; failed and
timed-out tests are reported honestly.
FR-10 — Agent Execution Timeline
Display real timestamped stages such as issue analysis, file retrieval, patch generation and test completion. Use
Server-Sent Events. Acceptance: events originate from backend execution; failures are clearly marked; progress
is not simulated.
FR-11 — Patch Evidence Report
Include repository and issue, investigation summary, files inspected and changed, diff, test commands, output,
exit status, duration and PR URL if available. Acceptance: every completed run has a report; untested changes
are explicitly labelled.
FR-12 — Pull Request Creation
After patch review and explicit approval, create or retrieve the user's fork, create a branch, commit the patch
and open a PR against the original repository. Acceptance: correct base branch; no direct write to original
repository; PR URL returned; no automatic merge.
FR-13 — Beginner Contribution Mode
Allow language and experience selection; recommend suitable issues; explain them simply; identify files and
provide learning steps. Acceptance: explanations are understandable and difficulty is labelled as an estimate.
This feature is deferred if core MVP delivery is at risk.
FR-14 — Screenshot-to-Bug Analysis
Allow validated image upload and multimodal Gemma analysis where supported. Link findings to repository
investigation. Acceptance: use only a verified image-capable endpoint; a screenshot is not treated as proof of
execution.

7.3 AI Layer
Selected model: Gemma 4 through a supported API. Responsibilities include issue understanding, classification,
duplicate analysis, code reasoning, relevant-file selection, root-cause investigation, patch generation, PR
descriptions and screenshot analysis where supported.
 • Structured JSON outputs and schema validation.
 • Prompt versioning and bounded context.
 • Timeout and retry policies.
 • Token and request usage tracking.
 • Tool permission validation.
 • No unrestricted shell execution.

8. High-Level Architecture
The system consists of a React frontend, Express backend, GitHub integration service, Gemma integration
service, repository retrieval service, controlled agent orchestrator, Docker execution worker, MongoDB database
and DigitalOcean infrastructure.
8.1 Controlled Agent Stages
 Stage
Responsibility
Issue Analyzer
Understand and classify the issue; extract expected behaviour.
Repository Investigator
Retrieve repository structure and relevant source files.
Root-Cause Analyzer
Propose likely causes with supporting evidence and uncertainty.
Patch Generator
Generate and validate a code diff; apply it to a temporary workspace.
Test Validator
Run approved tests in Docker and capture results.
PR Preparation
Prepare title and description, request approval and create PR.
These are stages coordinated by one backend-controlled orchestrator. They do not need to be separate
autonomous agents. Gemma may request a tool action, but the backend validates permissions and executes it.

10. Non-Functional Requirements
Security
 • Secure authentication and session handling.
 • Server-side credential protection and least-privilege GitHub permissions.
 • Input validation, rate limiting and audit logging.
 • Treat repository content and issue descriptions as untrusted input.
 • Validate every model-requested tool action.
 • Sandbox isolation and path traversal protection.
 • No production secrets in test containers.
 
Reliability
 • Graceful API failure handling.
 • Timeouts for model requests.
 • Retry only safe operations.
 • Idempotency for publishing operations.
 • Persistent agent run status.
 • Clear recovery from failed stages.
 
Performance
 • Paginate GitHub results.
 • Limit repository context retrieval.
 • Use background jobs for long-running work where needed.
 • Stream progress updates.
 • Avoid unnecessary repeated model requests.
 
Maintainability
 • Modular service architecture.
 • TypeScript types and Zod validation.
 • Consistent error handling and structured logs.
 • Environment-based configuration.
 • Unit and integration tests.
 
Usability
 • Beginner-friendly explanations.
 • Visible agent progress.
 • Clear patch review.
 • Understandable test output.
 • No hidden publishing actions.

14. Acceptance Criteria and Definition of Done
The MVP is complete when the following end-to-end workflow succeeds:
 ☐ A user connects a public GitHub repository.
 ☐ The application retrieves actual repository metadata and open issues.
 ☐ The user selects an issue.
 ☐ Gemma 4 analyzes the issue.
 ☐ RepoPilot retrieves relevant source files.
 ☐ The agent generates a proposed patch.
 ☐ The patch is validated and applied to a temporary workspace.
 ☐ Docker executes the configured tests.
 ☐ Actual test output and exit status are captured.
 ☐ A Patch Evidence Report is generated.
 ☐ The user reviews and approves the patch.
 ☐ RepoPilot creates a branch in the user's fork.

16. Final Product Definition
RepoPilot is a repository-aware AI engineering agent designed to simplify open-source contributions. It helps
developers and maintainers transform reported software issues into investigated, tested and review-ready
contributions.
Gemma 4 provides AI reasoning and code generation. GitHub provides source repositories and
contribution workflows. React provides the developer experience. Node.js and Express
coordinate the system. MongoDB stores application data. Docker provides isolated testing.
DigitalOcean provides cloud infrastructure.
Defining Differentiator
The Patch Evidence Report: every proposed contribution should explain what changed, why it changed and what
validation actually occurred.
Final Product Statement
 RepoPilot helps developers and open-source maintainers transform reported software
issues into investigated, tested and review-ready contributions while keeping humans in
 control of every published change.
