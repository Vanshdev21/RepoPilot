RepoPilot
 An AI teammate for open-source software projects
A detailed, beginner-friendly project guide — written for readers
 who may know HTML and CSS but have never used GitHub.
The idea in one sentence
RepoPilot connects to a public GitHub project, understands a reported software
problem, asks Gemma 4 to investigate the code, prepares a possible fix, tests that
fix in a separate Docker environment, and — after a human approves it — can
prepare a GitHub pull request.
Important: RepoPilot is an assistant for developers. It does not get permission to change somebody
else's project automatically, and it must never claim that a fix works unless tests were actually run.

1. Start with the problem: why does
RepoPilot exist?
Imagine that someone builds a free website, tool, or library and shares its source code so other people
can use it. After a while, a user reports: “The upload button crashes when I select a large file.” The
project maintainer now has to understand the report, find the right part of the code, reproduce the
error, write a fix, test it, and review the change.
That work can take hours. A beginner who wants to help may not even know which file to open.
RepoPilot is designed to make that journey easier.
A simple analogy
Think of a software project as a large school building. Its rooms are folders, the
objects inside the rooms are files, and the instructions for how the building works
are its code. A bug report is like a note saying, “The lights in Room 12 do not turn
on.” RepoPilot is a trained assistant who reads the building map, visits the likely
room, investigates the problem, suggests a repair, and checks whether the lights
work afterwards.
The project has two main beneficiaries:
 • Maintainers: people responsible for keeping a software project working. RepoPilot can help them
 investigate and prepare fixes.
• Contributors: people who want to improve a project. RepoPilot can explain unfamiliar code and guide
 them towards a useful contribution.
RepoPilot does not replace the maintainer. It prepares work that a person can inspect and approve.

3. What exactly will RepoPilot do?
The main feature is called Issue-to-PR. It means helping turn a reported problem into a proposed code
contribution. Here is the journey in simple steps.
Step 1 — Connect a public project
The user pastes a public GitHub repository address, such as github.com/owner/project. RepoPilot
retrieves basic information: project name, description, main programming language, README and
file/folder list.
Step 2 — Choose a reported problem
RepoPilot retrieves the project's open issues. The user selects one issue. An issue is simply a report or
task. For example: “The application crashes when a user uploads a large image.”
Step 3 — Understand the report
Gemma 4 reads the issue title and description. It identifies what is going wrong, what the expected
behaviour might be, and what information is missing. It can classify the issue as a bug, feature request,
documentation task or question.
Step 4 — Investigate the source code
RepoPilot searches the repository for files that may be related to the issue. It reads only the relevant
files rather than blindly sending the entire project to the AI. It can inspect filenames, functions, imports,
tests and documentation.
Step 5 — Explain the likely cause
Gemma 4 receives the issue and relevant code. It prepares a reasoned explanation of where the
problem may be and why. This is a hypothesis, not proof. The developer can inspect the files and
explanation.
Step 6 — Propose a code change
The AI suggests a patch. A patch is a small, structured description of exactly which lines should be
added, removed or changed. RepoPilot checks that the patch refers to permitted files and does not
escape the temporary project folder.
Step 7 — Test the proposed change
RepoPilot applies the patch to a temporary copy of the repository and runs approved test commands
inside Docker. It records the command, output and exit status. A passing test is useful evidence, but it
does not prove that every possible bug is fixed.
Step 8 — Prepare a pull request
If the user approves, RepoPilot can create a branch in the user's own fork, commit the changes and
open a pull request against the original project. The original project owner decides whether to accept it.
Step 9 — Produce an evidence report
RepoPilot displays the issue, files changed, explanation, code difference, test commands, test results
and pull-request link. This makes the work easier to review.

4. What is Gemma 4, and why does
RepoPilot need it?
Gemma 4 is an AI model family from Google. An AI model is software trained to understand and
generate information. Depending on the model and the way it is accessed, it can work with text,
images, reasoning tasks and code-related requests.
In RepoPilot, Gemma 4 acts like the investigator and problem-solving assistant. It is not the database,
not GitHub, and not the computer that runs tests. It analyses information and recommends what should
happen next.
A simple comparison
Imagine a mechanic. The customer describes a car problem, the mechanic reads the
service manual, inspects the car, recommends a repair and asks a technician to
perform checks. Gemma 4 is the reasoning mechanic. GitHub provides the project
information. RepoPilot's backend coordinates the work. Docker is the safe test
workshop.

Does the AI directly control the computer?
No. This is a crucial safety decision. Gemma 4 can request an action, but the Node.js backend decides
whether that action is allowed. For example, the model may request that a file be read. The backend
checks the path, reads the file and returns its contents. The model does not receive unrestricted access
to the server.
Why use an API instead of running the model on our own computer?
An API lets our application send a request to a hosted model service and receive a response. This is
quicker to set up for a one-day hackathon than downloading model weights, configuring inference
software and managing hardware. The exact Gemma 4 model name, API endpoint, supported input
formats and tool-calling format must be checked against the provider's current documentation before
integration.
A model response can be wrong. RepoPilot must validate its output, inspect patches,
run tests and show uncertainty honestly.

How the parts talk to each other
The browser sends a request to the Express backend. The backend retrieves data from GitHub or
MongoDB, and sends relevant information to Gemma 4 when AI analysis is needed. If a patch needs
testing, the backend asks the Docker worker to run an approved test. The results are saved and sent
back to the browser.
What is an API?
An API is a defined way for two software systems to communicate. Think of it as a waiter in a restaurant:
you make a request from a menu, the waiter passes it to the kitchen, and brings the result back. The
frontend does not need to know how the backend performs every task.

6. Docker: the safe testing room
A repository may contain code written by people we do not know. Running that code directly on the
main application server would be dangerous. A test command could delete files, consume too much
memory, or attempt to access sensitive information.
Docker lets us run a program inside a container: an isolated environment with its own filesystem and
controlled resources. It is like giving a visitor a separate workshop instead of letting them freely enter
the entire building.
The intended test process
 • Create a temporary copy of the selected repository.
 • Apply the proposed patch only inside that temporary copy.
 • Start a preconfigured, non-privileged test container.
 • Run an allow-listed test command, such as a known npm test script.
 • Capture the output, exit code and duration.
 • Stop and remove the container and temporary workspace.
 
Safety rules
 • Do not run containers in privileged mode.
 • Do not mount the host's Docker socket into the test container.
 • Do not pass GitHub tokens, API keys or production secrets into the container.
 • Disable network access for tests unless a specific, reviewed need exists.
 • Set CPU, memory, process and time limits.
 • Run as a non-root user where possible.
 • Do not automatically run a Dockerfile supplied by an unknown repository.
 • Check every generated file path and reject attempts to write outside the workspace.
 Honest reporting: “Tests passed” means the selected commands completed
successfully in the configured environment. It does not mean the software is
guaranteed to be bug-free. If tests were not run, the report must say “Not tested.”
7. How GitHub permissions and pull
requests work
A public repository can be read by anyone, but that does not mean everyone can change the original
project. RepoPilot should respect the owner's permissions.
For the initial workflow, the user connects their GitHub account. RepoPilot creates or uses a fork — the
user's own copy — then creates a separate branch, adds the proposed change and opens a pull request
to the original project.
A pull request is a request for review, not an automatic acceptance. The original maintainers can
comment, ask for changes, reject it or merge it. RepoPilot must never promise that a pull request will be
accepted.
The user must explicitly approve the proposed changes before RepoPilot publishes a
branch or opens a pull request. Access tokens stay on the server, are protected, and
are never included in AI prompts.

8. What makes RepoPilot different?
The project should not be presented as “a chatbot that can read GitHub.” Its value is the complete,
reviewable workflow. Three features help make that clear.
A. Repository understanding
RepoPilot reads the project's README, folder structure and selected source files. It uses the issue to
decide which files are relevant. This is more useful than sending random files to an AI model and hoping
it understands the project.
B. Issue-to-PR workflow
The agent moves through investigation, proposed fix, patch validation, testing and pull-request
preparation. The interface should show each stage and the real result. This is the central feature to
demonstrate to judges.
C. Patch Evidence Report
Every run produces a report that answers: What issue was selected? What files were examined? What
changed? Why was the change suggested? Which test command ran? Did it pass? Is there a
pull-request link? This gives reviewers evidence instead of asking them to trust a vague AI claim.
Optional extra: First Contribution Copilot
A beginner can choose a language or skill level and ask RepoPilot to find a manageable issue. The tool
can explain the issue in simple words, identify relevant files and provide a learning path. This is a useful
addition if the core workflow is already reliable.
What RepoPilot will not try to do in the first version
 • It will not support every programming language on day one. The first reliable runner should focus on
 Node.js projects.
• It will not automatically merge pull requests.
 • It will not run untrusted code on the main application server.
 • It will not guarantee that every AI-generated patch is correct.
 • It will not require blockchain. Blockchain does not solve the core problem in this version.

10. The system architecture in plain
language
The architecture is the plan showing how the different pieces of RepoPilot connect. The diagram below
is a simplified view of the proposed system.
USER'S BROWSER
React dashboard: repository input, issue list, agent progress, patch review and
report.
EXPRESS BACKEND
Receives requests, checks permissions, coordinates GitHub, Gemma, database and
Docker.
GEMMA 4 API
Analyses issue and relevant code; proposes a cause, patch or next action.
GITHUB
Provides public repository information, issues, forks, branches, commits and pull
requests.
DOCKER WORKER
Runs selected tests in a temporary isolated container and returns output.
MONGODB
Stores users, repository metadata, run status and evidence reports.
DIGITALOCEAN
Hosts the web application and backend; can store generated artefacts in cloud
storage.
Why use one agent orchestrator?
The first version will use one backend-controlled workflow with several stages: issue analysis, code
investigation, patch generation, test validation and pull-request preparation. These stages can use
different prompts and structured outputs, but they do not need to be separate autonomous agents. This
is simpler to build, test and explain in a one-day hackathon.
How progress reaches the screen
The backend can send progress updates to the browser using Server-Sent Events (SSE). SSE is a
one-way live connection: the server can tell the browser “Reading files”, “Generating patch” or “Tests
completed” without the browser repeatedly asking for updates.
Why DigitalOcean?
DigitalOcean is the cloud provider selected for hosting the application. The hackathon version can use it
to run the frontend and backend and, if time allows, store reports or other files in cloud object storage.
Gemma 4 inference is planned through its supported API, so a GPU server is not required for the initial
version.
The exact deployment arrangement must be tested. A Docker execution worker
needs access to a Docker runtime; do not assume every application-hosting service
permits launching nested containers. If the chosen hosting plan cannot safely run
the worker, deploy the worker separately on a suitable host.

14. Frequently asked questions
Do I need to know GitHub to use RepoPilot?
No. The interface should guide the user through connecting a public repository, choosing an issue and
reviewing the proposed fix. Some GitHub concepts are useful, but the guide and interface explain them.
Does RepoPilot write the entire application?
No. It investigates a specific issue and proposes a focused change. A developer still reviews the change
and decides whether to publish it.
Can it fix every bug?
No. Some issues need more context, special hardware, external services or human judgement.
RepoPilot should say when it cannot confidently investigate an issue.
Does a passing test prove the patch is correct?
No. It proves only that the selected tests passed in the configured environment. Other tests or
real-world conditions may still reveal a problem.
Can RepoPilot change the original public repository directly?
Not unless the user has permission. The planned workflow creates a branch in the user's fork and opens
a pull request to the original repository.
Why is Docker needed?
It provides a separate environment for running project tests so untrusted code is not executed directly
on the main application server.
Why use Gemma 4?
It is the selected AI model for understanding issue descriptions, analysing code context, reasoning
about possible causes and generating proposed changes. Its exact API features must be verified before
implementation.
Why use DigitalOcean?
It is the selected cloud platform for deploying the application and supporting infrastructure. The project
should demonstrate real cloud hosting, not merely display a DigitalOcean logo.
Why no blockchain?
Blockchain is not necessary to solve the core problem. Adding it would increase complexity without
improving the central issue-to-PR workflow.
What happens if the AI is wrong?
The backend validates its outputs, the patch is displayed for review, tests are run in a sandbox and a
human must approve publishing. The evidence report must show failures honestly.
