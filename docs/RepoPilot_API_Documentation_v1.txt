From GitHub issue to verified, review-ready pull request.
This document defines the HTTP API for RepoPilot: a repository-aware AI engineering agent that connects to public
GitHub repositories, investigates issues, proposes code patches, runs tests in an isolated Docker environment,
produces an evidence report and prepares a pull request after explicit human approval.
Document status: This is a detailed API design aligned to RepoPilot PRD v1.0. The PRD defines endpoint families and
product requirements; request/response fields, status codes and several operational details below are proposed
contracts for implementation and should be treated as the v1 API specification.

1. Overview and design principles
RepoPilot exposes a versioned REST API under /api. The React client calls the Express/TypeScript backend. The
backend owns GitHub credentials, validates all requests, coordinates Gemma 4, retrieves bounded repository context,
validates patches, delegates test execution to a restricted Docker worker and stores execution evidence in MongoDB.
Principle
API consequence
Human approval first
Creating a pull request is a separate, explicit action after review; no automatic merge.
Evidence over claims
Test status is based on actual command output, exit code and duration. Untested changes are labelled.
Backend-controlled tools
The model can suggest an action; the backend validates and executes only allowlisted operations.
Bounded context
Repository files and issue text are retrieved selectively and size-limited.
Public repository MVP
Only public GitHub repositories are in scope for v1.
One orchestrator
Agent stages are coordinated by one backend workflow, not separate autonomous agents.
1.1 High-level request flow
Browser → Express API → authentication/authorization → GitHub service and repository retrieval → agent
orchestrator → Gemma 4 service → patch validator → Docker worker → evidence report → user approval → GitHub
fork/branch/commit/PR.
1.2 Scope boundaries
Included in v1: GitHub OAuth, public repository connection, open issue discovery, issue classification, repository
investigation, root-cause hypotheses, patch generation, patch validation, Node.js Docker test execution, event
streaming, evidence reports and approval-gated PR creation. Private repositories, automatic merging, enterprise team
management, arbitrary language runners and browser-based IDE functionality are out of scope.
Important: A successful test run means the selected command passed in the configured sandbox. It does not prove that
the patch is defect-free or that every possible test passed.

Application resource IDs are opaque strings (MongoDB ObjectId serialized as a string is acceptable). GitHub

3. Authentication and authorization
Authentication uses GitHub OAuth. The backend exchanges the OAuth code, stores GitHub credentials securely
server-side and creates an application session. The frontend receives only the application session or secure cookie.
OAuth state must be random, short-lived and validated to prevent CSRF.
3.1 Permission model
 Capability
Required access
Read public repositories and issues
Public read access; no write permission required.
Fork repository
Authenticated GitHub identity and permission to create a fork.
Create branch/commit in user's fork
Write access to the user's fork.
Open pull request against upstream
GitHub permission to create a PR from the fork; upstream repository must accept contributions.
Merge pull request
Not supported by RepoPilot v1.
3.2 Authorization rules
Every protected request must resolve the authenticated user from the server-side session. A user may access only
their own agent runs, reports and connected-repository records. Do not trust userId supplied in a request body. Verify
ownership on every runId/repositoryId lookup. GitHub OAuth tokens must never be logged, returned in API payloads
or sent to Gemma 4.

6. Authentication endpoints
6.1 POST /auth/github
Purpose: complete the GitHub OAuth callback exchange. In a standard browser OAuth flow, GitHub redirects to a
backend callback route with code and state. If the frontend posts the code, the backend must still validate state and
redirect origin.
Request body
 {
  "code": "github_oauth_authorization_code",
  "state": "random_state_value"
}
Response — 200 OK
 {
  "success": true,
  "data": {
    "user": {
      "id": "usr_...",
      "githubId": 12345678,
      "username": "octocat",
      "avatarUrl": "https://avatars.githubusercontent.com/u/...",
      "name": "The Octocat"
    },
    "session": { "expiresAt": "2026-11-07T09:30:00.000Z" }
  },
  "meta": { "requestId": "req_..." }
}
The session should normally be set as a Secure, HttpOnly, SameSite cookie. Do not include the GitHub access token
in this response.
Possible errors: 400 OAUTH_STATE_INVALID, 401 OAUTH_CODE_INVALID, 502 GITHUB_PROVIDER_ERROR, 429 RATE_LIMITED.
6.2 GET /auth/me
Returns the authenticated application user. Response data contains user id, GitHub id, username, avatar URL and
display name. Returns 401 when no valid session exists.
 {
  "success": true,
  "data": {
    "id": "usr_...",
    "githubId": 12345678,
    "username": "octocat",
    "avatarUrl": "https://avatars.githubusercontent.com/u/...",
    "name": "The Octocat"
  }
}
6.3 POST /auth/logout
Invalidates the application session and clears the session cookie. Response: 200 { success: true, data: { loggedOut:
true } }. Logout should be safe to retry.

7. Repository endpoints
7.1 POST /repositories/connect
Purpose: validate a GitHub URL and connect a public repository. The backend normalizes owner/name, checks
visibility, retrieves metadata, README and a bounded file tree, then stores a repository record.
Request
 {
  "repositoryUrl": "https://github.com/owner/repository"
}
Response — 201 Created
 {
  "success": true,
  "data": {
    "repository": {
      "id": "repo_...",
      "githubRepositoryId": 123456789,
      "owner": "owner",
      "name": "repository",
      "fullName": "owner/repository",
      "htmlUrl": "https://github.com/owner/repository",
      "defaultBranch": "main",
      "primaryLanguage": "TypeScript",
      "description": "Example repository",
      "visibility": "public",
      "readmeSummary": "A short repository summary.",
      "indexingStatus": "completed",
      "connectedAt": "2026-10-31T09:30:00.000Z"

Validation: accept canonical github.com repository URLs only; reject malformed URLs, unsupported hosts, private
repositories and repository paths that do not identify owner/name. Do not accept arbitrary clone URLs or execute
repository scripts during connection.

Returns the connected repository record and current indexing metadata. Response includes id, fullName, description,
defaultBranch, primaryLanguage, readmeSummary, indexingStatus and lastIndexedAt. Return 404 if absent or not
owned by the caller.

7.5 Repository retrieval limits
The repository retrieval service should fetch the README, tree and likely package manifests first. Source retrieval is
bounded by file count, file size and total model-context budget. Exclude binary files, generated bundles, vendor
directories, node_modules, secrets and files above configured limits. Store paths and retrieval metadata so the
evidence report can explain which artifacts were inspected.
8. Issue and analysis data models
8.1 Issue classification object
 {
  "category": "bug",
  "summary": "Refresh requests may fail during Redis retry.",
  "expectedBehavior": "A valid refresh token should be retrieved or a typed error returned.",

  "missingInformation": ["Reproduction frequency", "Redis client version"],

  "confidence": 0.78

category enum: bug, feature_request, documentation, enhancement, question, other. severity enum: low, medium,

9. Agent execution endpoints
The agent workflow is a backend-controlled state machine. A run is created asynchronously and progresses through
real stages. The client should not infer completion from elapsed time or animated UI.
9.1 POST /agent/analyze
Starts an agent run for a selected issue. The endpoint validates ownership of the connected repository and confirms
the issue exists. It creates a persistent run record and queues or starts the orchestrator.
Request
 {
  "repositoryId": "repo_...",
  "issueNumber": 128,
  "options": {
    "includeDuplicateCandidates": true,
    "maxFilesToInspect": 20
  }
}
Response — 202 Accepted
 {
  "success": true,
  "data": {
    "runId": "run_...",
    "status": "queued",
    "currentStage": "issue_analysis",
    "createdAt": "2026-10-31T09:30:00.000Z",
    "eventsUrl": "/api/agent/run_.../events",
    "statusUrl": "/api/agent/run_..."
  }
}
202 means the run was accepted, not that the AI analysis succeeded. The frontend should subscribe to events and/or
poll the status endpoint.

9.4 Cancellation
Cancellation is a recommended extension for long-running runs: POST /agent/:runId/cancel with an empty JSON
body. It should stop future stages, request worker termination, preserve completed evidence and mark the run
cancelled. If cancellation is not implemented in the first MVP, the UI must not show a cancel control.
10. Patch review and test execution
10.1 Patch representation
The API should persist a patch artifact with a base commit SHA, file paths, unified diff and validation state. Prefer
unified diff for display and Git application; keep any structured file-change representation internal if needed.
 {
  "patch": {
    "format": "unified_diff",
    "baseCommitSha": "4a9bc81f...",
    "files": [
      {
        "path": "src/auth/session.ts",
        "status": "modified",
        "additions": 8,
        "deletions": 2
      }
    ],
    "diff": "diff --git a/src/auth/session.ts ...",
    "validation": {
      "valid": true,
      "applied": true,
      "errors": []
    }
  }
}
Allowed file statuses: added, modified, deleted, renamed. Reject absolute paths, ../ traversal, symlink escapes,
unexpected binary changes and changes outside the temporary workspace. Recheck base commit SHA before
applying or publishing.
10.2 POST /agent/:runId/test
Starts or retries test execution for a validated patch. v1 initially supports Node.js repositories using predefined runner
images and allowlisted commands. The backend must not execute arbitrary Dockerfiles or arbitrary model-provided
shell commands.
Request
 {
  "testProfile": "node-default",
  "commands": ["npm ci", "npm test"],
  "timeoutSeconds": 600
}

11. Approval and pull-request publishing
11.1 POST /agent/:runId/approve
Purpose: record explicit user approval to publish the currently reviewed patch. Approval is scoped to the exact patch
hash and base commit SHA.
Request
 {
  "patchSha256": "sha256-of-reviewed-patch",
  "baseCommitSha": "4a9bc81f...",
  "approved": true
}
Response — 200 OK
 {
  "success": true,
  "data": {
    "runId": "run_...",
    "approval": {
      "approved": true,
      "approvedAt": "2026-10-31T09:50:00Z",
      "patchSha256": "sha256-of-reviewed-patch"
    },
    "publishingEligible": true
  }
}
If the patch changes after approval, approval is invalidated and the user must review and approve the new patch. If
tests have not run, the API may permit an explicit risk acknowledgement only if the product chooses to support that;
the recommended v1 default is to require a completed test result or clearly mark the patch untested and block
publishing.
11.2 POST /agent/:runId/pull-request
Creates a branch in the authenticated user's fork, commits the approved patch and opens a pull request against the
original public repository. This operation requires explicit approval and an idempotency key.

14.2 Agent run state machine
 queued
  -> running
       -> awaiting_review
            -> completed          (user chooses not to publish / report finalized)
            -> publishing
                 -> completed     (PR created)
                 -> failed        (publishing failed)
       -> failed
       -> cancelled
The exact terminal state policy should be implemented consistently. Recommended distinction: workflow execution
ends at awaiting_review; after user action, the run becomes completed when finalized, or remains awaiting_review
until the user approves or dismisses it. Publishing failures should preserve the evidence and allow a safe retry.
14.3 Data consistency rules
Store the repository default branch and base commit SHA used for analysis. A patch is valid only against the base
SHA it was generated from. If upstream changes before publishing, compare the current base and either
rebase/revalidate or reject as stale. Approval binds to the patch hash and base SHA. A PR URL is populated only after
GitHub confirms creation.

17. Idempotency, pagination and rate limits
17.1 Idempotency
Require Idempotency-Key for POST /agent/:runId/pull-request. Strongly recommend it for POST /agent/analyze and
POST /agent/:runId/test. Store the key, authenticated user, route, normalized request hash and result. Repeating the
same key and same request returns the original result. Reusing a key with a different request returns 409
IDEMPOTENCY_CONFLICT.
17.2 Pagination
GitHub issue listing uses page/perPage. Cap perPage at 100 and prefer a smaller default. Return hasNextPage and
optionally totalCount only when the upstream API can provide a reliable value. Do not fetch all repository issues by
default.
17.3 Rate limiting
Apply per-user and per-IP limits. Suggested starting limits (tune after measurement): repository connect 10/minute;
agent run creation 5/minute and 20/hour; test execution 5/minute; PR creation 3/minute; general read endpoints
60/minute. These are proposed operational defaults, not PRD-defined requirements. Return 429 with Retry-After.

19. End-to-end integration example
The following sequence illustrates the expected client workflow. It is an integration example, not a claim that these
endpoints have already been implemented.
 # 1. Connect a public repository
POST /api/repositories/connect
{ "repositoryUrl": "https://github.com/owner/repository" }
# 2. List issues
GET /api/repositories/{repositoryId}/issues?page=1&perPage=20
# 3. Start analysis
POST /api/agent/analyze
{ "repositoryId": "{repositoryId}", "issueNumber": 128 }
# 4. Subscribe to events
GET /api/agent/{runId}/events
Accept: text/event-stream
# 5. Fetch current run snapshot
GET /api/agent/{runId}
# 6. Start tests after patch validation/review
POST /api/agent/{runId}/test
{ "testProfile": "node-default",
  "commands": ["npm ci", "npm test"],
  "timeoutSeconds": 600 }
# 7. Retrieve evidence
GET /api/reports/{runId}
# 8. Approve the exact patch
POST /api/agent/{runId}/approve
{ "patchSha256": "...", "baseCommitSha": "...", "approved": true }
# 9. Publish a PR (explicit user action)
POST /api/agent/{runId}/pull-request
Idempotency-Key: <unique-key>
{ "title": "Fix issue #128", "body": "..." }
19.1 Frontend state guidance
The frontend should treat API responses as the source of truth. Use the run snapshot to hydrate page state, then
apply SSE events. On reconnect, fetch the latest snapshot. Disable approval until a patch is available and reviewed.
Disable PR publishing until approval is valid. Display test status exactly as returned: passed, failed, timed_out or
not_run.
